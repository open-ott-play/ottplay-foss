# Private favorites receipt ledger v2

This freezes the player-owned serialization used by `favorites-recovery-codec.ts`. It adds no wire operations, permissions or backend guarantees by itself.

The physical key remains `favorites-receipts.v1`. A first actually guarded mutation may create `{entries: [...], version: 2}` from absent storage. Reading absence returns logical format 2 and SHA256 of UTF-8 `null`, with zero records; it writes nothing and establishes no producer provenance. Non-absent input must be exactly the JSON.stringify serialization of a validated `{version, entries}` object, retaining its physical key order. Duplicate keys, whitespace normalization, invalid Unicode, unknown fields, more than 32 entries and more than 65536 UTF-8 bytes fail closed.

Original v1 rows keep their original schema. New rows add exactly `fence: {backendProof: <64 lowercase hex>, guardImplementationVersion: 1, version: 2}`. A row without that field remains legacy even in a v2 envelope. Envelope version 1 forbids fences/audits. New service reservations capture the trusted host's `fence()`; every physical service write additionally requires `writeGuard(fence) === true` under the same captured actual exclusive grant. Neither field is supplied by the public request.

Original-row canonical bytes are compact JSON of all original row properties recursively sorted by ASCII key, excluding ONLY the root `recovery_ack` property. All permitted private keys are ASCII. Nested arrays retain their order. No original values, receipt data, fence or timestamps are omitted. Whole-ledger revision instead hashes its exact original raw UTF-8 serialization, never this canonical projection.

The only added audit is `recovery_ack`, with fields inserted in this exact order: acknowledgement_id, backend_proof, ledger_revision_before, reason, runtime. Values use the public revision-2 contract; runtime is `[a-z0-9-]{1,64}` and reason is `accept-unknown-no-replay`. There is no timestamp, after digest, plan digest, random value or placeholder. The ACK and PLAN domain arrays follow `favorites-recovery-design-20261028/v2/operations.md` exactly. Backend domain binds actual origin, private key, private lock name, kind, private format 2 and implementation version 1.

Acknowledgement appends only this audit to the selected row in the existing parsed ledger. JSON.stringify then reproduces every other row and original property in the same order. The entire maximum added audit is 377 UTF-8 bytes plus the 16 bytes for `,"recovery_ack":`, totalling 393. Every unacknowledged pending/partial/unknown v2 row reserves 1024 bytes inside 65536, including during pending plans, completion planning/materialization and each actual write. Existing nonconforming ledgers remain readable but cannot authorize acknowledgement or automatic admission/completion repair. Acknowledgement consumes only its selected reserve; it frees no entry slot and changes no original outcome.

Pending, partial and unknown rows are protected regardless of age; acknowledged protected history remains protected and counts toward 32. Only proved verified/not_applied originals may be evicted under admission pressure. Late completion/reservation proofs cannot mutate a legacy or acknowledged row. All mutation receipts retain replayAllowed:false. Global exclusion of NEW operations while any unacknowledged protected row remains is enforced by the physical host/runtime admission, separately from the service's owned pending-to-completion transition.

Pure API: `createFavoritesRecoveryCodec({sha256(text):Promise<hex>})` returns `snapshot(raw)`, `inspect(raw,{runtime,operationId,backendProof})`, `backendProof(grant)`, plus synchronous parse/capacity/originalCanonical. Snapshot returns all protected rows (including acknowledged history), sorted by UUID. It validates stored audit ACKs against their stored runtime/L/B/reason and immutable original; an observing runtime may differ. Inspect returns no plan for missing, legacy, acknowledged, unqualified, mismatched-backend or insufficient-capacity rows. No function initializes storage, creates admissions, caches write tickets or performs writes.
