# Connect to a command server

The separate [OTT-play Control Server](https://github.com/open-ott-play/ottplay-control-server) provides per-player command queues, portable server binaries, Docker images for amd64/arm64, and Kubernetes/k3s packages. It follows the optional `local_proxy.py` example and adds separate administrator/device credentials and acknowledged delivery.

For a prepared installation, use **Settings → Remote control → Find command server** and approve the displayed pairing code; no controller address or token needs to be typed on the player. See [discovery and one-time approval](#discovery-and-one-time-approval) and the [operator runbook](#operator-runbook-no-address-entry-on-the-player). Discovery availability depends on the player variant and deployment described below.

For manual setup, open **Settings → Remote control → Command server**. Enter the server IP, hostname, or HTTP(S) address and this player's device access code from the server configuration. Saving the second field starts polling immediately; either field can be entered first. For example, enter `192.168.1.20` for a server listening on the default HTTP port 8081, or `192.168.1.20:9000` for a different port. Use the device's `token`, never the server's `admin_token`.

This access code is neither the iPhone unlock PIN nor the **Device access code** generated by **Local HTTP remote control**.

Changing the address or access code reconnects automatically once both fields are present and valid. Clear either field or select **Disconnect** to stop. Cancelling an edit, saving an unchanged value, or reopening the settings does not reconnect a deliberately disconnected client. Select **Connect** to resume without changing the saved values. An enabled connection resumes when the player starts again.

Bracketed IPv6 and a reverse-proxy base path are accepted. An old full command endpoint is normalized to the new acknowledgement endpoint. Credentials belong in the separate masked access-code editor, never the address. The status shows a missing field, connection progress, access denial or a transport error.

This connection is disabled by default and independent of the local HTTP listener. It works without WebCrypto because the server supplies the access code. The player stores the address, code and enablement on this device only. JSON exports, cloud exports and local backups omit them, including nested backups from older versions. Importing or restoring settings disconnects the connection and cannot grant consent or import another installation's credentials; the current device's address and code remain available for an explicit reconnect.

## Delivery behavior

When idle, the player polls about once per second with an 8-second transport timeout, non-overlapping requests and bounded retry backoff. A known request backlog drains without the idle delay while yielding between responses; repeated or invalid queue entries retain the idle cadence. Acknowledgement removes commands only after dispatch or explicit rejection. Repeated IDs are deduplicated during a running page session, including reconnects with the same server and access code; failed acknowledgements are retried without repeating the action. Changing the address/code or disconnecting cancels the active generation, so a delayed old response cannot control the player.

Commands that need channels wait while the provider is loading. The server supplies its current time and command expiry, so an incorrect TV clock does not extend command lifetime. Older compatible responses have a bounded local waiting period. Expired commands are retired without dispatch.

Volume, channel selection, notifications and provider selection use the existing player paths. Provider selection retains parental controls and Android Play restrictions. M3U playlist replacement updates the actual active M3U entry and reloads it; other providers report unsupported. Generic `change_provider_settings` has no shared provider schema and is explicitly unsupported. An acknowledgement reports handling/rejection, not confirmed playback, PIN approval or hardware state. Deduplication is not persistent across a player restart.

## Transport requirements

- Browser/TV: XMLHttpRequest uses the ES5 runtime loaded before the player. The server must allow the exact page origin. Packaged pages with a null Origin need the server's explicit device-only opt-in.
- Tauri: the existing native `proxy_http` bridge carries both polling and acknowledgement requests.
- Capacitor: the existing native HTTP bridge carries both methods. Android Play and iOS transport restrictions remain enforced.
- An HTTPS web page cannot poll a plain HTTP server. The UI explains the failure; use an HTTP player page on the trusted LAN or an HTTPS command-server endpoint.

The [hosted player](https://player.ottplay.here.now/) needs an HTTPS command-server
endpoint. Local player installations use HTTP ports 8443–8446. The central OTT
server's command routes remain disabled; the command server is a separate
process/service. Hosting discovery metadata on here.now does not move that service
or remove the player's need to reach its advertised controller address.

## Discovery and one-time approval

In the web-based player (including Tauri and Capacitor packages), an installation
without a saved command-server address, token or enabled connection starts one
nonblocking discovery attempt after its device UUID is available. Existing
settings, including an explicit disconnect, are preserved. In Remote control, **Find
command server** (shortcut **6**, or LEFT/RIGHT and OK) deliberately retries discovery
and can stage a replacement for incorrect manual settings. Nothing is replaced until
the selected server grants approval. **Cancel pairing** retires pending callbacks.

### Shared DNS-SD descriptor

The service type is `_ottplay-ctrl._tcp`. Native DNS lookup queries that service
under the network's configured search domains; it does not scan IP ranges or
guess a controller hostname. The service name is project-specific, not an
IANA-registered public standard. An example zone uses:

```dns
_ottplay-ctrl._tcp.home.arpa. IN PTR home._ottplay-ctrl._tcp.home.arpa.
home._ottplay-ctrl._tcp.home.arpa. IN SRV 0 0 443 controller.example.com.
home._ottplay-ctrl._tcp.home.arpa. IN TXT "txtvers=1" "scheme=https" "path=/ott-control"
```

Replace the example domain and target with the operator's actual values. The
PTR identifies the instance, and SRV plus TXT produce its HTTPS base address.
The target is a DNS hostname with a trusted TLS certificate, not a literal IP.
A/AAAA records provide IPv4/IPv6 reachability for that hostname; the descriptor
and pairing procedure are the same for both address families. Successful
metadata lookup does not prove that either address family can reach the HTTPS
service. Do not put credentials in DNS or substitute an IP that fails TLS
hostname verification.

In the current desktop/core implementation, search domains come from macOS
System Configuration, Windows DNS settings, or Linux `/etc/resolv.conf`. DNS
queries use the operating system resolver; no public DNS server is substituted.
The network must supply the intended search domain as well as working DNS.
A reachable controller alone is insufficient if that domain is missing. This
is search-domain DNS-SD, not an automatic browser mDNS or `.local` scan.

Advertise the search list through DHCPv4 option 119; retain an existing option 15
domain where clients need it. For IPv6, the DNSSL/search-list advertisement
supplies suffixes, while RDNSS supplies DNS resolver addresses; one does not
replace the other. Let clients receive an ordinary lease renewal or router
advertisement rather than forcing a connection reset or reboot. Keep an
external controller hostname's A/AAAA records pointing to its actual service:
do not replace them with the router's address to make multicast advertisements
appear to work.

The controller's [DNS-SD setup guide](https://github.com/open-ott-play/ottplay-control-server/blob/main/docs/discovery.md)
covers publishing the records and configuring its optional discovery/pairing
service. A browser profile transports the same version-1 descriptors over HTTP;
it does not give the browser a DNS-SD API.

### Lookup by platform

- **Tauri:** `discover_control_servers` reads DNS-SD `_ottplay-ctrl._tcp` records
  from the network's discovery domains first. A valid nonempty result takes
  priority over the deployment profile. A valid empty result tries the configured
  profile URL once; without that profile it stops as unavailable, even on a
  loopback origin. Malformed native metadata fails without fallback. A rejected or
  thrown native call takes the browser lookup path described below.
- **Browser, PWA and LG webOS browser:** use the explicit deployment profile when
  present. Otherwise, only pages on `localhost`, `127.0.0.1` or `[::1]` try
  `/api/control-discovery` on their own origin. That route belongs to the local
  OTT Server and can discover through its host; a static web server need not
  provide it. Other page origins require an explicit profile. Browsers do not
  call the Tauri native DNS command.
- **Capacitor iOS/Android:** uses the browser lookup and Fetch pairing path too.
  The native HTTP bridge used by ordinary command polling does not replace this
  discovery transport. A packaged app must receive its own deployment profile;
  installing the app does not copy the hosted website's profiles or credentials.
  A distribution can embed an explicit profile through the build options below.

**OTTPlay Native is a separate implementation from Tauri and the LG browser.**
Linux DNS-SD support is being integrated separately in
[the Native delivery candidate](https://github.com/open-ott-play/ottplay-foss/pull/1014);
it is not supplied by the shared-player changes described here. Verify that the
installed Native build includes it before relying on this path. In that candidate,
**Find command server** queries `_ottplay-ctrl._tcp` through the system resolver.
This is unicast DNS-SD, not multicast mDNS, and does not require a new multicast
responder. Readable `/etc/resolv.conf` or `/var/run/connman/resolv.conf` supplies
the search domains; otherwise libc's own suffix search is attempted. A slow
suffix may exhaust the shared three-second discovery deadline. A timed-out
resolver can still be finishing, so a new Find may temporarily be refused.

Only a successful empty DNS result can try the optional public catalog configured
with `PLX_CONTROL_DISCOVERY_URL` and `PLX_CONTROL_DISCOVERY_SHA256`. Resolver errors,
malformed or oversized answers and timeouts do not trigger that fallback. The
catalog's exact response digest is checked before its descriptors are read.
macOS Native and builds without Linux DNS-SD support retain the catalog path.
Native Find remains explicit and requires server selection even for one row;
this change does not add the web player's automatic first-run attempt, change
saved settings or bypass pairing approval. Publishing a web profile alone does
not configure a Native catalog.

Empty or invalid metadata from the browser lookup stops the attempt; it does not
start another lookup loop. Tauri DNS lookup and its profile fallback share one
15-second discovery deadline. Each HTTP request is bounded to eight seconds.
Neither finding a server nor loading a profile enables remote control by itself.

### Deployment profile and here.now

Before the player initializes, a deployment may set a string URL:

```javascript
// Example custom deployment; replace with its actual published metadata URL.
window.__OTT_CONTROL_DISCOVERY_URL__ =
    "https://player.example.net/control-discovery.json";
```

The response is public metadata, for example:

```json
{
  "version": 1,
  "servers": [{
    "id": "home._ottplay-ctrl._tcp.example.net.",
    "domain": "example.net",
    "address": "https://control.example.net/ott-control"
  }]
}
```

Use the actual controller descriptor; inventing an ID does not register a server.
The list is bounded to 16 entries. Every advertised controller must have an HTTPS
base address without embedded credentials, query or fragment. A metadata-level
`pairing_url` cannot override the selected controller's `/api/pairings` route.

The companion [web deployment repository](https://github.com/open-ott-play/ottplay-web-vitrine)
owns the Home profile. Its generated `local/hosted.js` selects an absolute
`https://player.ottplay.here.now/local/control-discovery.<sha256>.json` URL.
The fingerprint identifies the exact metadata content. Use the
[Home discovery setup and runbook](https://github.com/open-ott-play/ottplay-web-vitrine/blob/main/docs/home-control-discovery.md)
for the exact URL and deployment checks; do not replace `<sha256>` with an
arbitrary value.
Generic player builds contain the lookup mechanism, not this Home-specific
configuration. To include a reviewed public profile in a particular web, server,
Tauri, Capacitor or Tizen distribution, set both build variables explicitly.
The following pair selects the public Home profile prepared for the Native
delivery candidate; it is an opt-in deployment choice, not a universal default:

```sh
export OTTPLAY_CONTROL_DISCOVERY_URL="https://player.ottplay.here.now/local/control-discovery.0a3bf94cadba71fdd02af4783574ea4690de2839a3eaa05a2bea18a715eb2e4d.json"
export OTTPLAY_CONTROL_DISCOVERY_SHA256="0a3bf94cadba71fdd02af4783574ea4690de2839a3eaa05a2bea18a715eb2e4d"
```

Other operators supply their own HTTPS catalog URL and reviewed raw-content
digest. This pair identifies a reviewed build input; it does not prove the
current website response or an installed application's configuration.

Pass the pair in the build environment. With both variables unset, no profile is
injected. A partial or invalid pair fails before assembly. The configured build
initializes `window.__OTT_CONTROL_DISCOVERY_URL__` only if the deployment has not
defined it, and includes the initialization before calculating the common bundle
identity. Explicit deployment values, including an empty value, remain intact.
These settings supply discovery metadata only; they do not replace saved player
settings or authorize a connection.

The digest records the operator's reviewed catalog selection in
`window.__OTT_CONTROL_DISCOVERY_SHA256__` alongside the injected URL; both values
participate in the bundle identity. This marker is build metadata. The browser
transport validates the response schema and HTTPS delivery but does not
independently verify its response digest. The separate Native delivery candidate
retains its explicit URL/SHA-256 catalog fallback and runtime digest verification.
The hosted LG webOS launcher loads the canonical website and uses that site's profile.

Publishing the website does not update an installed app's bundled frontend.
Rebuild and install that distribution to change its packaged profile. See
[delivery by platform](discovery-deployment.md) for reload, package, signing and
installation-preservation requirements.

Prefer absolute HTTPS URLs when sharing a profile across hosted, local and native
players. A relative URL resolves against the **player page**, not the script that
sets it. The metadata URL may have a query, but cannot contain credentials or a
fragment; HTTP is accepted only for same-origin metadata. Cross-origin Fetch
requires CORS on the metadata endpoint and on the controller's public pairing
endpoints. Static metadata loading successfully does not prove pairing is allowed,
since the endpoints can be on different origins. An opaque `Origin: null` needs
the controller's `allow_null_origin` option, which also covers its public device
discovery/pairing routes. Non-null WebView origins need an explicit allowed origin.
Redirects are not a supported way to forward discovery or pairing.

The frontend exposes `window.__OTT_CONTROL_DISCOVERY_VERSION__ = 1` for deployment
compatibility checks. This marker neither enables a connection nor identifies the
exact build containing the Tauri native-empty-result fallback. Site publication,
fingerprint retention and cache handling are documented in the companion
[release workflow](https://github.com/open-ott-play/ottplay-web-vitrine/blob/main/docs/release-workflow.md).

Network DNS/search domains and the deployment discovery profile are trusted
installation configuration. HTTPS proves control of the advertised hostname, not
the controller operator's identity. An untrusted network or profile could nominate
its own HTTPS controller and approve its own pairing. Use discovery on trusted home
or managed networks; saved/manual controller settings remain pinned elsewhere.
Approval by the legitimate controller protects its existing device credentials,
but DNS discovery alone cannot cryptographically authenticate that controller.

Discovery responses contain addresses, never device tokens. Multiple servers remain
an explicit choice. The player sends `{device_id,server_id}` to the selected base's
`/api/pairings`, displays the eight-character approval code, and waits for the operator
to approve it. For an already registered CLI alias, use `ott approve NAME CODE`.
With an enabled device registry, a new alias can instead be enrolled and approved
with `ott registry approve NAME UUID CODE`, using the administrator CLI profile.
First match the expected player's full UUID and displayed code against
`ott -j pending`. A request's UUID is self-declared; confirm the physical player's
identity and code rather than approving by UUID alone.
The short-lived pairing secret stays in memory and authenticates readback and
receipt cleanup; it is not rendered, logged or persisted.
An approved response must match the exact device and selected HTTPS address and carry
a valid device token before the existing command-server controller saves and enables it.

Pairing expires within ten minutes. Discovery and HTTP requests have bounded timeouts;
transient readback retries never repeat the pairing POST. Editing settings, changing
the device UUID, disconnecting, canceling or beginning a newer discovery retires old
callbacks. The settings page may be closed while approval is pending and reopened to
see its status. EPG, provider loading and remote text entry do not depend on discovery
being available.

Canceling, replacing a pairing, or successfully saving approved settings sends a
best-effort authenticated DELETE for the receipt with a two-second timeout. A failed
settings save retains the receipt privately until an explicit cancel/retry; server
expiry remains the fallback if cleanup cannot reach the server. Same-origin metadata
GETs include `X-Ottplay-Discovery: 1` so legacy local browsers with a no-referrer policy
can use the discovery route without enabling cross-origin access to that route.
HTTPS discovery and pairing use a dedicated no-redirect transport: Tauri applies
HTTPS-only native requests, while browsers and Capacitor use Fetch with
`redirect: "error"`. Browsers without this capability show a manual-setup message
instead of sending pairing credentials through XHR. An AbortController is also
required so cancellation and timeouts stop the underlying request. Same-origin HTTP metadata
discovery remains available on local installations, and existing manually configured
command connections and provider transports retain their behavior.

### Operator runbook: no address entry on the player

Use the operator's network runbook for the deployed DNS/DHCP configuration and
maintenance steps. Follow the client procedure below with the network's
advertised service; do not duplicate router configuration in a player.

1. Publish the controller's PTR/SRV/TXT records under the intended network search
   domain and enable its discovery/pairing configuration. Ensure the advertised
   HTTPS hostname, port and path match the controller's public URL and certificate.
   Use the controller setup guide above; DNS records contain public metadata only.
2. Prepare the lookup path for each deployed variant. Tauri, the local OTT
   Server and Linux Native builds with DNS-SD support need the correct OS search
   domain and resolver. Supply the domain through the network's DHCP search-list
   option (119) or IPv6 router-advertisement search list as appropriate. Existing
   clients receive changes after lease renewal or a subsequent advertisement;
   check their actual resolver configuration before retrying. Changing multicast
   advertisements alone does not configure this unicast lookup. Hosted/browser
   and Capacitor installations need their deployment profile, except for the
   local loopback route above. Other Native builds need the build-bound catalog.
   Configure CORS for the actual browser/WebView origin where Fetch is used.
3. Choose a distinct CLI alias for this installation. A static controller needs
   the player's full UUID registered before pairing; an enabled device registry
   also supports enrollment at approval as described above. Do not reuse another
   player's alias or token, or copy an administrator token into the player.
   Verify the advertised HTTPS service is reachable from the player's network
   over the available address family.
4. On a fresh web-based installation, allow the initial lookup to complete. For
   an existing installation or an explicit retry, select **Find command server**.
   Select the intended server when offered; the web player starts pairing directly
   for a single result, while Native Find always requires selection. Check the
   displayed server, full device UUID and code before using the appropriate
   registered-alias or registry approval command above.
5. Wait for approval and the saved, enabled connection. Finding a server, displaying
   a code or approving the wrong installation is not connection confirmation.
   Cancel if the server is unexpected. If discovery fails, repair the domain,
   profile, HTTPS or build configuration and retry Find; do not disable TLS checks
   or repeatedly erase working settings.

This runbook moves endpoint configuration to the network/deployment operator;
it does not remove that prerequisite or promise discovery on every network.
Keep a previously paired installation intact while testing a fresh deployment.

### CLI checks and preset transfer

The terminal must already be configured for the intended controller:

```sh
ott -j discover
ott -j pending
```

`discover` queries that configured controller; it does not bootstrap an unknown
server or search for players. `pending` lists existing pairing requests and does
not authorize them. Keep each installation's alias separate: for example, retain
`l` for the existing player and use `l_` for a new Native installation with its
own full UUID and credentials. Match the screen's code and identity before
approving; do not approve an unknown request automatically.

After the connection is confirmed, a saved composite preset can be transferred
with a plan and a durable checkpoint. Replace the example alias and preset with
your actual values. Here `local` is a case-insensitive saved preset name, not the
Local-files provider; the example preset's M3U `active_profile` determines what
opens. Replace `/PRIVATE_DIR` with a private directory restricted to its owner
(mode `0700`); keep checkpoints out of shared repositories and logs.

```sh
ott l_ load local plan
ott l_ load local apply --checkpoint /PRIVATE_DIR/l_-local.json
ott l_ load local verify
# Only when recovering the same incomplete operation:
ott l_ load local resume --checkpoint /PRIVATE_DIR/l_-local.json
```

`plan` inspects the preset's local structure; it is not a Native compatibility
check. `apply` requires command-journal support and compares all parts before
its first mutation, but subsequent steps are not atomic. If preflight is
unsupported, stop rather than falling back to a bare load. Recover an uncertain
operation with the same preset, device and checkpoint using `resume`.
`verify` is read-only; it does not prove visible playback or every arbitrary UI
setting. If saved Favorites require the CLI's explicit `--settings-only` option,
use it consistently in every mode only when deliberately skipping Favorites;
that is not a complete preset import, and the flag must not be added silently.

### Troubleshooting discovery

1. **No automatic attempt after an update:** saved address/token/enablement or an
   earlier attempt in this page session suppresses automatic lookup. Use **Find
   command server** deliberately; do not erase a working connection to test a
   new deployment profile. Pending discovery leaves that connection intact.
2. **No server found:** check which platform path above ran and whether its build
   includes native DNS-SD. An empty DNS result with no profile is terminal. In a browser, a 404 from `/api/control-discovery` means the
   local host does not supply the route; configure the deployment profile or enter
   the controller manually. A valid empty list is not a connection success.
3. **Invalid response or URL:** check version `1`, the server descriptor and the
   actual metadata response rather than an HTML fallback page. Non-string profile
   values and insecure controller addresses cannot trigger pairing. A malformed
   native result is not retried against the profile to hide the error.
4. **Metadata loads but approval fails:** inspect the selected controller's
   reachability, TLS and public-pairing CORS for the actual page/WebView origin.
   On older LG browsers, verify Fetch, Request, AbortController and support for
   `redirect: "error"`; otherwise use the offered manual configuration path.
   The here.now hostname supplies no extra native or TLS capability.
5. **Timeout, cancellation or changed settings:** correct the network/profile and
   use **Find command server** for a new attempt. Late responses from the previous
   attempt cannot save a connection. Keep the displayed approval code private and
   approve it only for the expected player on the intended controller.

For an already connected player, `ott PLAYER caps` and
`ott PLAYER inspect --view ui,media` provide capability/build observations without
re-pairing. Test fresh discovery in a separate test installation/profile if the
existing connection must remain untouched. The source regression suite
`node tests/test_control_discovery.cjs` covers native priority/empty/error cases,
invalid profiles, approval, cancellation and deadlines, including ES5 parsing.
Those checks do not establish successful discovery or playback on a physical LG
TV, iPhone, Android device or a particular network.

## Compatibility maintenance

TypeScript uses descriptive English names. `src/compatibility/legacy-names.ts` declares the established provider-script globals, popup action IDs and version-1 backup fields. The classic linker preserves those external names, while live aliases let both interfaces observe provider hook replacement. Stored keys, DOM IDs, provider-specific fields and action identities retain their existing contracts.

Validate source behavior, emitted provider ABI, persisted settings, ES5 syntax and actual transport separately. `tests/test_english_naming.cjs` covers source names, shadowed bindings, classic emission, live aliases, action identity and backup round trips. The command-server and dispatcher suites cover retries, stale responses, boot readiness and provider restrictions. Physical TV/STB transport and playback remain device acceptance checks.

## Terminal CLI and replies

The optional protocol-1 request extension supports `ott NAME v`, `s`, `p`,
channel selection by catalogue number/name, provider listing/selection,
M3U profiles, playback restarts and explicit M3U/Xtream/Stalker/OTTClub settings
adapters. See the
[CLI guide](https://github.com/open-ott-play/ottplay-control-server/blob/main/docs/cli.md).
The terminal's alias maps to the device UUID in the local CLI configuration;
device registration and credentials belong to the controller.
Each installation needs its own code. No administrator token belongs in a player.

`ott NAME fav add` saves the currently playing channel or film with its provider
and profile. `ott NAME fav` lists saved entries; `ott NAME fav play NAME_OR_ID`
loads the saved profile and resolves the item again before dispatching playback.
See [remote favorites across profiles](remote-favorites.md) for examples,
persistence and troubleshooting.

With the CLI's central EPG service configured, programme searches request only
the player's channel metadata and use the service's `/epg/v1/current` endpoint.
See [remote EPG control](remote-epg-control.md). Without that configuration,
queries use the player's current catalogue and guide service; EPG requests have
a 25-second collection budget and report partial results explicitly. Programmes
share the Unix-seconds `as_of` timestamp captured when collection starts, even
when guide callbacks arrive later. `checked` counts completed channel lookups;
`partial: false` means collection completed, not that every feed has EPG. The
guide service can return an empty result for either missing data or a fetch
failure, and neither appears in the programme list. Read results
exclude stream URLs and provider secrets. Provider settings use the active
driver and preserve parental/distribution policy. A successful dispatch reply
does not prove playback or hardware state. HTTP result retries do not repeat
a command within one page session; restarting a player clears deduplication.
Retries send the same serialized result bytes. Invalid or oversized handler
results are explicitly rejected so polling can continue. EPG collection yields
between batches, keeps at most four guide requests pending, and rejects results
if the source or channel-load generation changes during collection.
The previous command-only API remains compatible with older servers and players,
except that unacknowledged `exit_player` is now explicitly unsupported. Modern
`command: exit_player` uses the acknowledged native exit path; it never toggles standby.

### Safe random playback

Update the player, controller and CLI together for safe random selection. The
player advertises `caps.random.version: 1`; older players must be updated instead
of receiving an unverified random fallback.

```sh
ott t1 R                      # same as: ott t1 random
ott t1 random 1 1000          # uniform selection within this inclusive range
ott t1 provider m3u R         # switch provider, then select from its complete All catalog
ott t1,t2 provider m3u random # select independently on both players
ott t1 provider m3u "News"    # exact full name first; otherwise random matching title
```

Random selection runs inside the player against its current catalog and uses
only eligible channels. Titles containing the literal `[AceStream]` marker are
excluded case-insensitively. Existing access restrictions remain in effect,
including when a local access session is already active. The player retains
its existing playlist metadata precedence and manual-selection behavior.

Without a range, 80% of selections use eligible catalog numbers 1–1000 and 20%
use the remaining eligible numbers, uniformly within each group. When one group
is empty, selection uses the other. An explicit range is uniform across eligible
numbers in that range. Numbers come from the complete All catalog, including
Plex and VPortal; filtering does not renumber them. A title filter prefers exact
case-insensitive full-name matches, otherwise substring matches. An excluded
exact match does not fall through to unrelated partial matches.

An empty pool, stale catalog, changed provider, standby, kiosk or access
restriction rejects playback without selecting an ineligible alternative. A dispatch
reply confirms admission, not successful decoding. Inspect `ott t1 caps` and
refresh the catalog or resolve the local restriction before retrying.

The negotiated request is `play_catalog` with
`{"catalog":"RECEIPT","random":{}}`; optional `search` and `[from,to]` `range`
belong inside `random`. Existing `{"catalog":"RECEIPT","id":"ID"}` requests
retain manual-selection behavior. The older `random_channel` command retains
its current-list scope with the same safe filter.

### Named controls and platform capabilities

`ott NAME caps` reports the current player version, public page-runtime identity,
and available lifecycle, input and playback operations. The same player identity
is included in `status`; it is observable metadata, never an access credential.
Short and full channel queries retain case-insensitive literal matching, including
Cyrillic. The CLI also accepts exact command aliases such as `v` / `vol` / `volume`,
`s` / `channels`, `profile` / `prof` and `key` / `input`. Use `play TITLE` when a
channel name is reserved by a command. Malformed recognized commands fail explicitly.

`reload` / `restart player` reloads the page; `restart app` relaunches the native
application; `exit` / `quit` closes a supported app; `standby` / `wake` controls
player standby while its connection stays active. `reboot device` means an OS
reboot and is currently unsupported on every shipped platform. No command falls
back to a different lifecycle operation, and wake cannot wake an offline device.

Tauri advertises native exit/restart only after the shell answers a read-only
capability probe, so newer web code in an older shell remains compatible.
Android Capacitor exit requires the actual native media exit method; the separate
native Android app does not automatically gain this shared frontend feature.
Packaged Tizen and LG webOS can advertise their verified app-exit API. Ordinary
browsers and iOS do not advertise native exit or application relaunch.

Lifecycle and named input effects wait for the exact server acknowledgement,
then recheck current restrictions and ownership. An accepted reply is not proof
that the effect completed. Repeated result delivery does not replay the effect;
an expired acknowledgement, changed screen or revoked permission may cancel it.
Named keys follow the existing player UI; unmapped keys and hardware collisions
are unavailable. PIN entry, browser capture-source selection, exit confirmations
and private settings import/export/reset screens require local interaction.
Use explicit typed lifecycle commands for remote exit or reload.

`ott PLAYER prev` / `previous` and `ott PLAYER next` select the adjacent channel
in the currently playing category or favourites, wrapping at either end. They
use typed playback operations `previous_channel` and `next_channel`, not UI
keys: an admitted switch closes the channel list, even if another category is
being browsed. The receipt contains `{operation,dispatched:true,channel:{id,number,name}}`;
`number` is the catalogue number from `s`. An unloaded/stale selection, protected
UI/PIN, standby, kiosk or settings lock rejects the step. `prev` is list order,
not viewing history. A single-channel category selects the same channel.

`ott PLAYER +15` and `ott PLAYER -15` move by a signed offset in that same
playing category, wrapping as many times as needed. With 100 channels, channel
100 plus 15 selects 15, channel 1 minus 15 selects 86, and channel 5 minus 15
selects 90. The player selects the final destination once; it does not play
intermediate channels. A complete turn, or any offset in a single-channel
category, selects the current channel once.

The wire request is `playback` with exactly
`{"operation":"step_channel","offset":15}`. `offset` must be a nonzero JSON
integer between -9007199254740991 and 9007199254740991. The receipt adds the
exact requested `offset` to `{operation,dispatched:true,channel:{id,number,name}}`.
The destination still uses the playing category order; the receipt's `number`
remains the global catalogue number. `caps.playback` includes `step_channel`
when the selection state permits relative commands, even if adjacent channels
need a PIN. Every actual destination is checked independently; protected or
stale requests are rejected without a deferred PIN continuation.

Both the controller and player must support these operations. They appear in
`caps.playback` when available and as `prev` / `next` in the bare `ott PLAYER`
overview. A lost response is never retried as a new mutation. Existing
`key ch+` / `key ch-` keep their UI-dependent behavior, including list pagination.

`pause` and `resume` operate on current owned archive/VOD playback; `seek SECONDS`
uses the VOD timeline only. Live playback and archive seeking retain their existing
domain-specific controls. Capability availability can change between reading it
and issuing a command. These administrator controls do not expand scoped diagnostic
operator permissions. The enabled controller connection already authorizes diagnostics.

With `playback_seek_relative: {"version":1}`, an explicitly signed seek moves
relative to the current decoder position in one player operation:

```sh
ott l seek +10s             # forward 10 seconds
ott l seek -10s             # back 10 seconds
ott l +1m                  # forward one minute (signed-unit shorthand)
ott l seek +3m             # forward three minutes
ott l seek -1m30s           # back 90 seconds
ott l seek +1h30m           # forward 90 minutes
ott l seek 01:30            # absolute position at 90 seconds
ott t1,t2 seek -10s         # back 10 seconds on each player
```

`seek +10` and `seek -10` also accept plain seconds. Units are case-insensitive;
ordered `h`, `m`, `s` components, fractions such as `+0.5s`, and signed
`MM:SS` / `HH:MM:SS` clock times are supported. Each player in a list seeks from
its own current position; group commands do not synchronize playback.

The wire request is `playback` with exactly
`{"operation":"seek_relative","offset":30}`. The offset is a nonzero finite
number of seconds with absolute value at most 9007199254740991. A successful
receipt contains exactly `dispatched`, `operation`, `offset`, `from`, `position`
and `clamped`; it confirms dispatch to that owned decoder, not completed playback.
The relative operation uses only its new capability; `caps.playback` retains
the existing operation names for older clients. Bare `+30`
and `-90` retain their channel-step meaning; unsigned `seek 30` remains absolute.

Relative seeking requires playing or paused VOD with a known positive finite
duration and a seekable destination. It preserves pause state, clamps below zero
to zero, and clamps 1 ms before the end (to zero for shorter clips; a larger
floating-point guard is used for very large durations). It does not deliberately seek to EOF or advance
the queue; normal playback can still reach the end. Unknown duration, live/archive,
a pending decoder seek, standby or a changed source/decoder rejects the operation.
The shared HTML media path covers web, Tauri, Capacitor and LG; Video.js uses its
own guarded decoder path. This is capability-dependent, not a claim that every
device or media format supports seeking.

Authenticated absolute and relative VOD seeks are allowed in strict kiosk, while
parental/settings PIN restrictions and protected local-input dialogs still block
them. Other kiosk controls are unchanged. Clients do not emulate relative seek
with a status read or key presses and do not retry an uncertain mutation. Repeated
delivery of the same request ID within the current player process replays the
saved receipt without applying the offset again.

For a playing or paused TV archive, an updated player instead advertises
`playback_seek_archive_relative: {version:1}`. Updated CLI commands such as
`ott l +1m`, `ott l -10s`, and `ott l seek +3m` use the same `seek_relative`
operation with the explicit additional field `timeline:"archive"`. This is a
separate contract; VOD requests and receipts keep their original format.

An archive receipt adds `timeline:"archive"`, `earliest`, and `latest` to the six
fields above. `from` and `position` are Unix timestamps in seconds, and the bounds
are inclusive integer timestamps for the currently retained archive. The player
rounds `from + offset` down to a whole second, then clamps to those bounds;
`clamped` describes that boundary clamp, not rounding. `latest` stays at least one
second behind the live edge. The CLI prints local dates and times. A large forward
seek therefore stays in archive mode; it never silently switches to live TV.

The archive controller resolves the provider URL at the new broadcast time, so a
finite decoder duration or native `seekable` range is not required. It can cross
programme boundaries and guide gaps while keeping the same channel. File-based
archives reopen the correct programme file and use its programme-relative offset.
Pause intent is supplied to the new decoder before asynchronous startup. Source
changes, expiry, standby, kiosk and PIN restrictions reject the request. A refused
synchronous request retires pending authorization/resolution callbacks; it cannot
start later. Install the updated relay, player and CLI together before using this
archive extension; an old relay rejects the extra timeline field without playing.

Updated clients additionally support `resolve_archive` and `play_archive_catalog`
for the CLI's channel → current programme → available archive search. Archive
resolution is a separate authenticated operation that returns a private media
URL only for a local availability probe; ordinary catalogue and guide replies
remain metadata-only. Playback uses the existing archive controller and validates
the current catalogue receipt, channel access and a maximum 144-hour retention.

### Aspect ratio

`ott PLAYER aspect` reads the current main-video mode. `ott PLAYER aspect fit`
uses **Fit to screen** (contain); `ott PLAYER aspect fill` uses **Fill screen**
(cover). Fill preserves the video's proportions and crops its edges. It does
not stretch the image or change the separate PiP window.

The shared HTML player supports this during an active main-video session in
Tauri, the OTT Server and here.now web frontends, and Capacitor iOS/Android.
Other device engines must advertise support;
the CLI never falls back to pressing a key or opening a menu.

The typed `aspect` request accepts exactly `{operation:"get",runtime}` or
`{operation:"set",runtime,mode:"fit"|"fill"}`. Obtain `runtime` from the current
player capabilities. `capabilities.aspect` contains `version:1`, an `operations`
array and a `modes` array. Unsupported players expose empty arrays; a locked
player may advertise only `get`. Kiosk mode, protected local dialogs and parental
settings locks prevent remote writes.

A successful set reply contains `{version:1,runtime,operation:"set",mode,
accepted:true,dispatched:false,effect:"aspect-after-ack"}`. Application and storage
wait for the server acknowledgement and recheck the playback target and access
policy. This reply confirms acceptance, not successful persistence. Read the mode
again to verify the result. A get reply contains `{version:1,runtime,
operation:"get",mode,saved_mode,persisted}`. `saved_mode` is `fit`, `fill` or
`null`; `persisted` is true only when backing storage contains the current mode.
Session-memory fallback does not count as saved.

Rejected and unsupported replies also bind to the current `runtime` and
`operation`; set replies include the requested `mode`. Their `error` code is one
of `invalid_request`, `runtime_mismatch`, `restricted`, `unsupported` or
`unavailable`. An older page's unbound reply cannot retire another page's request.

Preferences keep their normal scope: the current channel for live TV and a shared
media preference within the active provider/profile for VOD. The media setting
is restored for subsequent videos and after a player restart, including kiosk
restoration. Setting one live channel does not override all other channels.

### Local video profiles

`ott NAME provider local` selects **Local videos**; `offline` remains a compatible
alias and wire identifier. Save the connected source
selection and current video with `ott NAME profile save 1 Kids`, then restore it
with `ott NAME profile load 1` (or `profile 1`). Export with `profile export 1
kids.json`; import into an inactive slot with `profile import 2 kids.json`.
`profiles` lists the saved slots and whether local binding is required. The
`offline_profiles` capability advertises these operations. See [Local video
profiles](offline-profiles.md) for examples, same-device restoration, explicit
binding on another device and the portable format. Media files and file-access
grants are never included in these exports.

Updated CLI, controller and player builds also expose source commands through
the `local_media` capability:

```sh
ott NAME local sources
ott NAME local play Movies
ott NAME local shuffle Movies
```

Use an exact connected folder name or the source ID from the listing. Browser,
Android and iOS sources must already have their local file-access permission.
On Tauri builds advertising `absolute_paths`, `local connect /absolute/folder`
can register a readable directory on that target computer without starting
playback. `local sources --paths` explicitly includes private native paths for
configuration backup; ordinary listings omit them. Neither operation copies
media or transfers OS permissions. See [native source commands](tauri-local-media-sources.md#remote-local-videos-commands)
for limits and [local playback](offline-media.md) for platform setup.

`local_media_progressive: {version: 1}` is advertised only for the supported
Tauri backend, after its existing native source-capability check succeeds.
This selects the implemented remote early-playback path; it is not a new native
protocol negotiation. Partial playback still requires a matching source scan
generation, and a replaced or failed scan cannot extend the active queue.
Browser, server-backed and Capacitor Local sources retain ordinary Local and
session-only playback without this marker. Their remote commands await catalog
completion; an already active scan can report `catalog_loading`. The CLI enables
progressive playback only when the target advertises it.

### M3U profiles and restarts

Select M3U with `ott NAME provider m3u` before using profile commands.
`profiles` lists all 15 M3U slots, numbered 1–15 as in the player interface.
`profile 2` selects slot 2. An empty slot cannot be selected; configure its
playlist first. A deployment that fixes the M3U slot cannot select another slot.
Parental settings locks and provider distribution restrictions still apply.

`profile 2 url URL`, `profile 2 history HOURS` and `profile 2 name NAME`
change the specified slot. History is the playlist's archive depth in whole
hours (0–8760), not watch-history retention. Empty strings clear string fields.
Use `profile-config 2 FILE.json` to submit several settings together without
placing credentials in shell history:

```json
{"name":"Movies","playlist":"https://example.com/list.m3u","history_hours":72}
```

The settings object accepts only those three fields. Validation finishes before
anything is saved. Other fields and slots are preserved. Editing an inactive
slot does not select it or reload the active playlist. Responses contain only
the slot number, name, active state, archive hours and `playlist_configured`;
they never return playlist URLs. VPortal settings belong to the standalone
VPortal provider. M3U rejects `vportal` updates and preserves hidden legacy
portal fields. A valid link already stored in an M3U slot remains available to
Favorites through a lazy embedded VPortal client. Starting, refreshing or
selecting that slot does not itself fetch the portal catalog. See
[existing M3U portal links](m3u-vportal.md#moving-from-an-old-m3u-profile).

`ott PLAYER restart` reloads the complete player page, as do
`ott PLAYER restart player` and `ott PLAYER restart p`.
`ott PLAYER restart stream` (or `ott PLAYER restart s`) explicitly restarts
the current stream through its playback backend while preserving the supported
session state. Unsupported playback contexts report an error rather than
starting a different channel. The page-reload response means it was accepted; the
player performs it only after the command server acknowledges the response.
It does not claim that the replacement page has loaded or playback resumed.
Full reload has the same session behavior as the player's existing restart:
the in-memory VPortal automatic queue is not restored across page reloads.
An expired response or changed controller connection discards a pending reload.
Neither command retries a mutation after an uncertain response.

For an unattended player, use standby and go. The older `stop` / `start` and
`wake` aliases remain supported:

```sh
ott d1 restart stream  # Reconnect the current stream
ott d1 restart        # Reload the player, preserving standby if it is set
ott d1 standby        # Stop playback and suspend background media work
ott d1 go             # Resume the saved provider/profile startup once
ott d1 status         # Observe standby and background work state
```

Standby stops main/PiP playback, previews and queued autoplay, cancels provider
requests, local-library scans and programme-guide work, and prevents late results
or the kiosk watchdog from restarting them. New playback and scans remain blocked
until `go` or a local wake gesture. Clicking, tapping, or pressing a key on the
Standby screen uses the same wake path as `go`. The complete first gesture is
consumed: it does not change the channel, adjust volume, or activate an underlying
control. Pointer movement alone does not wake the player. Kiosk and settings
restrictions remain in effect after wake. Authenticated standby/go are available
in strict kiosk and with settings locked; app restart, exit, reboot and configuration keep their existing restrictions.
For Android hardware volume, D-pad, Back, Enter and media keys, install the updated
APK as well as the frontend. A web update cannot replace the old shell's native
key handling. Web tests verify tap/key dispatch, while physical button behavior
must also be checked on the installed device. The CLI's authenticated `key`
operation follows its separate remote-input restrictions and is not a substitute
for testing a physical wake gesture.
Remote polling, command replies and diagnostics remain available while the OS
keeps the app running. On iOS/Android the OS may suspend the app in the background;
`go` cannot wake a closed or suspended app, or an offline device. Standby controls
the player's work without shutting down the operating system. On browser and TV
runtimes without the native standby bridge, drain reporting covers tracked frontend
work; it does not stop shared OTT Server jobs or other clients. Native cancellation
requires an updated Tauri or Capacitor shell.

The player checkpoints its confirmed playback cursor before retiring the source.
Go reopens the saved source/profile through normal startup and resume rules; live
streams obtain a fresh URL. Repeated go does not launch a second startup. When a
valid interface language is already loaded, repeated standby/go reuses it and resumes
the configured provider without opening language settings. First-run setup and genuine
language-load failures retain their normal recovery flow. Standby
is saved only on this installation, so page/app reload stays asleep. Portable
settings and cloud backups neither import nor remove that state.
The normal Exit/Q action saves the playback position and closes the player
without entering standby; an awake player can resume normally on its next launch.

`status.player.standby` reports the state. On updated players,
`status.player.background` contains `state` and `pending`: `suspending` means tracked
work is still draining, `suspended` confirms zero tracked frontend/native jobs,
`running` means the player is awake, and `unsupported` or `error` does not promise
native quiescence. `running` confirms that the standby gate reopened, not catalogue
readiness or resumed playback; verify the saved selection and playback progress
separately. An accepted command only confirms delivery. Older native shells
must be updated for native HTTP, XMLTV and filesystem cancellation; the updated
frontend still blocks its own new work. A native acknowledgement timeout leaves
wake blocked with an error instead of silently starting against a sleeping backend.
Native startup checks the saved shell state before opening the provider, even if
the webview's settings were cleared. A native application update already downloading
cannot be cancelled by the updater API: it stays counted as pending until it finishes,
and its late result cannot relaunch an asleep player. New update checks/downloads are
blocked during standby.
Already-started browser script downloads and filesystem reads likewise remain
pending until their completion; their retired owners cannot resume playback.
An abandoned local-media request stops after its current filesystem operation.
An idle local HTTP response retained by an external client can remain pending
until that client reads or closes it; standby prevents further media reads.

If the backend supports restarting but has no current restartable stream, the
request returns `rejected` with `reason: "no_restartable_stream"`. This can happen
during startup or after playback ends; it does not mean the player lacks restart
support. Wait for a stream to load or explicitly request a full player reload.

These actions require updated CLI, control server and player versions. They
do not change the existing provider-selection or active-playlist commands.

### Remote diagnostic snapshots

Updated players include `status.playback` with the current playback state,
media kind, safe title/provider, optional media ID and channel number, timeline
position/duration, and volume. Unknown values are `null`. Titles describe the
confirmed playback owner, not a highlighted row or a pending selection. Pause
retains that owner; stop and standby clear the active media. Local labels expose
only a basename. URLs, absolute paths, credentials and raw provider requests are
excluded.
Unicode control/private characters are removed for URL/path classification,
while accepted display labels retain their original text. Older engines without
Unicode property support use conservative ASCII classification and may omit
ambiguous Unicode labels containing slashes.

A controller can advertise `player_state` version 1 in an authenticated command
poll response, with its `controller_epoch`, `/api/player-state` report path,
15000 ms heartbeat, 45000 ms freshness window and 4096-byte body limit. The player
then posts the same safe playback projection on connection and semantic changes,
plus a 15-second heartbeat. This uses the existing device credential and transport,
independently of notification settings. Older controllers receive no new requests.

Reports include the page runtime and an increasing sequence. Only one report is
in flight; subsequent changes coalesce. Retries preserve the exact body and
sequence. Changing controller configuration or epoch discards queued old reports,
and late replies cannot acknowledge a newer report. Disconnecting stops reporting;
the controller's last observation can remain available as stale history. Presence
does not establish physical power state or prove that video is visible.

The existing `status` request (`ott NAME` or `ott --json NAME`) retains its
`channels`, `provider`, `ready`, `uuid` and `volume` fields and adds an optional
`diagnostics` object with `version: 1`. It uses the same authenticated request
and response routes; no new server endpoint, credential or CLI action is needed.
Older players may omit `diagnostics`, and consumers must accept that omission.

The `epg` section reports whether hosted EPG diagnostics are `available` and
whether hosted EPG is `enabled` for this installation. When enabled, the snapshot
contains only `phase`, `failedPhase`, `elapsedMs` and `timingsMs` with separate
`cache`, `download` and `parse` durations in milliseconds. Error codes, byte and
programme counts remain in the player's local EPG diagnostics screen.
Phases are `idle`,
`starting`, `cache`, `waiting`, `download`, `parse`, `ready` and `error`; an
unrecognized phase is `null`. This describes the hosted XMLTV worker, not
native/provider EPG or proof that a particular channel has a current programme.

The `input` section reports whether the LG input snapshot API is `available`
and whether collection is `enabled`. Collection retains the existing local
opt-in through **Information → Debug HUD**. A status query does not enable the
HUD, install input listeners, change pointer visibility or start debug uploads.
Once enabled, the snapshot contains cursor/focus states (`on`, `off`, `unknown`),
page visibility (`visible`, `hidden`, `unknown`), pointer area (`in`, `out`,
`unknown`) and counts of move, down, click and wheel events delivered to the
page. Counts cover the current opted-in page session. Hiding the HUD does not
end that session or reset its counters.

`available: false` means the corresponding diagnostic API is absent.
`available: true, enabled: false` means the API exists but its feature or
collection is disabled; measurements are omitted.
`available: true, enabled: null` means the API exists but its enabled state or snapshot could not be read
reliably; measurements are also omitted.
`unknown` means no usable state has been observed, not that the cursor is hidden
or the TV is unfocused. Numeric counters and durations accept only finite,
nonnegative safe integers up to `9007199254740991`; invalid measurements are
`null`, not zero. Other unrecognized enum values are also `null`. A failed
diagnostic getter does not prevent the ordinary status fields from being returned.

Each producer creates a fresh snapshot with an explicit field allowlist; the
status handler reads those dedicated APIs, never the raw local diagnostics.
The diagnostics object excludes source
URIs, hostnames, filenames, playback URLs, query strings, credentials, extra
identifiers, raw error text and debug dumps. Pointer positions, typed keys and
individual input events are not returned. Snapshots are read-only observations;
an offline player cannot supply one, and an authenticated response does not
prove visible playback or physical remote behavior.

OTTClub's `server` is a bare host with an optional port, such as `club.example:8080`;
its existing driver supplies the URL scheme. Other supported providers accept
HTTP(S) URLs. Changing an OTTClub key preserves the stored host.

## Remote screenshots

Connecting and enabling remote control authorizes the configured controller to
troubleshoot the player, including screenshots. There is no separate screenshot
permission switch or ten-minute authorization limit. Update the player, command
server and `ott` CLI together; older players can still require their legacy local
grant. A platform without a capture adapter reports screenshots as unavailable.

1. Connect the player to the command server as usual. Screenshots require HTTPS;
   HTTP is accepted only for a controller on `localhost`, `127.0.0.1` or `::1`.
2. On supported native players, screenshots are immediately available and remain
   authorized after a restart while remote control stays enabled.
3. In a supported browser, choose the source in the browser's own sharing dialog.
   A local Connect action opens it when possible. For an already configured or
   reloaded page, use **Settings → Remote control → Select screenshot source in
   browser**. This selects a source; it does not grant additional player trust.
   The browser requires a local gesture and does not persist screen-sharing
   permission across reloads. See the [Screen Capture specification](https://www.w3.org/TR/screen-capture/#dom-mediadevices-getdisplaymedia).
4. Request one image:

   ```sh
   ott tv                         # shows operations and browser-source guidance
   ott tv caps                    # inspect screenshot readiness and capture source
   ott tv screenshot              # save one PNG under a unique local filename
   ott tv shot -o living-room.png  # short alias; an existing file is not overwritten
   ```

**Disconnect** in Remote control revokes the controller's access. Changing its
address or device credential invalidates pending images and browser selection.
Native capture automatically uses the newly configured connection. Browser
sharing lasts until it is stopped, its source ends, the controller changes or the
page reloads; it has no application-imposed ten-minute limit. **Stop browser
sharing** ends that source without disconnecting ordinary remote control.

The configured controller can capture the player's settings and text/PIN screens;
images can contain credentials and private information. Choose a browser source
carefully: another window or an entire display can include other applications.
Actual capture availability still depends on the OS, current source and adapter.
The player does not impose a foreground-only or protected-settings consent gate.

The response identifies the captured surface. Supported implementations differ:

- A browser with `getDisplayMedia` and `ImageCapture.grabFrame` captures the source
  selected locally. It reports
  `browser-tab`, `window` or `display`. A browser unable to identify its source,
  or without both working sharing and fresh-frame APIs, cannot provide this
  feature. Each request obtains a fresh frame from the live shared track; cached
  video-element frames and reconstructed DOM images are never substituted.
  Android browsers
  and a page hosted on here.now gain no native capability merely by connecting.
- macOS Tauri captures the player web view (`player-view`), not the desktop or
  other applications. Native overlays can be omitted; video inclusion is unknown.
- iOS Capacitor captures its visible WKWebView (`player-view`). Native video and
  native overlays are excluded. It rejects background capture and capture behind
  a native modal. There is no full-device recording or screen-recording prompt.
  The adapter passed an unsigned simulator-target build; screenshot capture has
  not yet been accepted on an iOS simulator or physical device.
- The archived Android Capacitor bridge includes an Android 8+ own-window adapter
  (`player-window`) using PixelCopy. It rejects protected, unfocused and inactive
  windows; protected video and separately composed surfaces may be absent. This
  repository does **not** build an Android APK. A compatible shell must integrate
  and package the adapter; the separate `ottplay-android` native app is not given
  remote screenshot support by this change.
- LG/webOS and other shells without a working capture adapter report
  `unsupported`; no simulated screenshot is substituted.

Images are PNG, at most 1280 × 720 pixels and 1 MiB before base64 encoding.
Downscaling may reduce the dimensions further. `video: "unknown"` does not promise
that video is included; `"excluded"` identifies an adapter that omits native video.
An image proves neither continuous decoding nor a healthy stream.

The player drops a result if its runtime or controller changes while capture is
pending. Native adapters allow one capture at a time and bound completion time;
a delayed platform callback cannot return an image after cancellation. The
image travels only in the authenticated command response. See the control
server's [CLI screenshot guide](https://github.com/open-ott-play/ottplay-control-server/blob/main/docs/cli.md#remote-screenshots)
for private local file creation and result-retention limits.
Screenshot uploads reject every HTTP redirect; configure the final HTTPS
controller URL directly. Disconnecting attempts to cancel an outstanding upload,
but cannot retract bytes already received by the controller.

If `ott tv` reports `permission_required` on an updated browser player, select a
source in the browser sharing dialog. Native players need an enabled secure
controller connection, not another approval. On an older player, update it or use
its previous permission flow. If a request is rejected, check the same runtime is
still running and the browser source is live. OS suspension, native modals or an
unavailable capture surface can still prevent capture. A timeout does not trigger
an automatic repeated capture. If a native adapter stays busy after a timeout,
restart the player: an outstanding platform capture retains its slot until its
callback returns. Native screenshots are authorized again automatically after
restart. Black or missing video can be a capture limitation; inspect playback
diagnostics separately. `unsupported` requires a supported browser or a newly
packaged native adapter.

New screenshot UI messages have English and Russian translations. Other language
catalogs currently use explicit English fallback for these new messages.

### Kiosk mode

Updated players, control servers and CLI builds support a device-local live-channel
lock, plus persistent VPortal and Plex media queues. Only an authenticated request delivered by the configured command server
can enable, replace or disable it. There is no local kiosk toggle.

```sh
ott tv kiosk on             # wait for the next admitted channel selection in the UI
ott tv kiosk on 12          # select and lock catalogue channel 12 immediately
ott tv kiosk on "Новости"   # lock the first matching name (case insensitive)
ott tv kiosk set 7          # replace the locked channel through the controller
ott tv kiosk status         # policy, channel metadata, health and retry count
ott tv kiosk off            # release the lock
```

With the VPortal or Plex provider selected, `kiosk on` without a channel query
captures the current video or complete media queue and repeats it. Start playback
first; an empty media library cannot be locked. For a shuffled Plex library, use
`plex play --shuffle ID...` before `kiosk on --strict`. Media kiosk stores source
requests and resumes the saved item/position when the application starts again.

The local watchdog retries after 10 seconds without playback progress, allowing
60 seconds for media startup and episode transitions. On a visible HTML video,
it also samples playback-quality or WebKit decoded-frame counters. After a
counter has advanced at least three times with gaps no greater than five seconds,
15 seconds without another non-dropped frame
stops treating an advancing media clock as healthy; the normal 10-second recovery
grace then applies. Paused/seeking/ended video, insufficient buffered data,
background pages, source changes and unavailable counters cannot trigger this
additional signal. These counters cannot prove that the display or audio hardware
is actually presenting output. The additive `video_progress` object in the raw
kiosk response reports counter source, state, counts and frame age, without media
URLs; older CLI versions may omit it from their formatted output.
After a frame stall triggers a retry, the same locked item retains its failure
state until ten seconds of steady frame progress. A counter that remains stuck
after that retry gets the 60-second startup grace before another attempt. Brief
bursts cannot clear the retry budget. Changing the locked item resets this state.

After three unsuccessful
stream retries, a subsequent stall reloads the player if its source still matches.
The reload first saves and verifies the locked selection and media position.
A persistent 10-minute cooldown prevents reload loops; stream retries continue
during that cooldown. While the runtime reports that the network is offline,
recovery waits instead of restarting. This cannot reconnect Android Wi-Fi or
repair an unavailable NAS. A provider that failed during offline startup can
reload after connectivity returns even before its catalog becomes ready.
An authenticated `ott tv restart player` also reloads
the player while retaining its saved kiosk policy.

Arming without a channel does not capture the already playing channel. The first
subsequent live selection that passes parental admission is retained, including
when that stream then fails to load. Repeating `kiosk on` without a channel leaves
an existing lock unchanged. Text queries select the first channel whose name
contains the query, ignoring case, in the catalogue order shown by `ott tv s`.
A later exact name does not take priority; duplicate matches are not randomized.
The query is a literal substring, not a regular expression or wildcard expression.
Numeric queries retain one-based catalogue numbering. No match, or an unavailable
or protected first match, rejects without changing the previous lock or skipping
to another match. Recovery retains the selected channel ID rather than rerunning
the name search.

The lock retains the source/profile identity and channel ID, not a list position
or expiring media URL. While enabled, provider/profile/settings mutations, media
queues, archives, ordinary remote channel commands and exit commands are rejected.
Once a channel is locked, local pointer/touch navigation and keyboard/remote
navigation are blocked; volume and mute keys remain available. Status, catalogue
queries, notifications, volume and explicit remote restarts remain available.
Use `kiosk off` before changing provider/profile or unlocking parental access,
then enable kiosk again on the intended channel. Parental restrictions still apply.

Add `--strict` for a child-facing player: `ott tv kiosk on --strict "Новости"`
locks the channel and permits a short tap or the Info key to show the video
footer for five seconds. In a media queue, tapping or dragging the footer timeline
seeks within the current episode. The gesture is cancelled if the episode, source,
player or policy changes; multiple fingers and vertical swipes cancel it too.
This exception requires the active core player and a known finite duration, and
stops one second before the end instead of directly triggering the next episode.
Outside the timeline, swipes and long presses remain blocked. Double-click actions,
pause, keyboard seeking, menus, player exit and local volume/mute controls
are blocked. Authenticated typed remote VOD seeking remains available under the
PIN, protected-dialog and ownership checks described above. In the Capacitor
Android app, physical Volume Up/Down keys control
Android media output directly, including while the page is locked or unresponsive.
Repeated taps never expand the description. Remote
volume/mute, status and recovery remain available; stopping the current diagnostic
capture remains available locally without disconnecting the remote controller.

`ott tv kiosk on --strict` upgrades an existing lock without changing its target.
For an unarmed TV player it waits for the first admitted UI selection, then blocks
input. `kiosk set CHANNEL` preserves strictness. Only the configured remote
controller can change or disable the policy, using `kiosk off` to release it.
The strict flag persists across reloads. The CLI requires an explicit strict
receipt and will not report success if an older player ignores this flag.

On the Capacitor Android app, screen-off or background state suspends locked
playback, releases its media transport and suspends recovery;
`screen_suspended` reports that state. This closes the player's HLS, DASH or
native media connection instead of leaving a paused player downloading into its
buffer. An in-flight request may finish during teardown. It does not stop a
shared camera relay or other viewers, and the remote control connection stays
available.

Returning to the foreground reconnects live TV/cameras at the live edge and
resumes films or archives from their saved position. A selection deferred while
asleep starts only after waking. Waking does not directly resume media that was
already paused; the normal kiosk recovery timer still applies. Changing only
strictness while asleep preserves this behavior
without waking the player. Ordinary pause outside this screen-suspension path
retains its usual buffering behavior.

This transport teardown requires an APK containing the screen-suspension fix;
`v1.1.55-beta.5` only pauses playback and can continue downloading while locked.
After installing an updated APK, validate with `screen_suspended: true` and
server-side byte/request counters over at least 30 seconds. A paused video or a
successful remote command alone does not prove that media traffic stopped.

On Android, a website (including here.now) cannot disable Home, Recents or browser
navigation outside its page. Use Android app pinning with a PIN to protect exit
from the browser, or managed-device Lock Task for a dedicated kiosk.

Legacy wrappers may intercept touch before it reaches the web player. If a
wrapper only requests the information footer without forwarding timeline
gestures, the footer remains read-only even with an updated player. Native
touch interception does not by itself establish Android system-exit protection;
check the wrapper's documented capabilities separately.

The separately provisioned [native maintenance agent](https://github.com/open-ott-play/ottplay-control-server/blob/main/native/android-agent/README.md)
has authenticated administrative recovery and queue operations outside the
ordinary web command lane. Native queue next/previous can move within the lock;
native queue stop explicitly releases it. Those operations are not local UI
exceptions for the viewer.

The client samples playback once per second. Ten seconds without playback position
advancing causes a fresh launch of the retained channel through the normal provider
resolver; unsuccessful attempts repeat at ten-second intervals. Healthy playback
is not periodically restarted. A missing channel or changed source never falls
back to another channel. The watchdog also survives decoder getter/resolver errors.
The inactivity sleep timer is suppressed while kiosk is enabled. The page/process
must remain running: this is a player watchdog, not an OS process supervisor, and
suspended browser pages cannot promise real-time timers.

The policy survives player reloads and remote-server outages and is excluded from
settings exports/imports. Disconnection does not release it. `kiosk off` must reach
the client to release it. A request receipt confirms stored policy and attempted
playback, not visible video. Updating only the command server cannot enforce this
policy on older clients.

The protocol-1 action is `kiosk`, with `params: {"mode":"status|on|set|off"}`;
`on` optionally accepts `query`, and `set` requires it. Both accept an optional
boolean `strict`; omission preserves the existing mode (ordinary for a new lock),
and an explicit `false` downgrades to ordinary kiosk without releasing the target.
`status` and `off` reject extra fields. Results include boolean `strict`.
`query` is a channel number
or name substring, limited to 1024 UTF-8 bytes. Read results expose metadata only.

### Hosted command transport

A hosted deployment can proxy player traffic through its own HTTPS origin when
its hosting service does not forward a caller's Authorization header. The
release ships `dist/control-transport.js` as a separate optional asset. Load it
synchronously after the deployment profile and before the player scripts.
Deployments opt in with reviewed public addresses only:

```js
window.__OTTPLAY_HOSTED__.controlTransport = {
  version: 1,
  endpoint: "/ott-control/api/device-transport",
  bases: ["https://player.example/ott-control", "https://control.example/ott-control"]
};
```

The adapter matches exact base paths. Other manually configured controllers
continue to use the direct transport. For matched requests it sends a versioned
JSON envelope to the same-origin endpoint, including the device token in the
HTTPS body and preserving the original method, path, query and JSON payload.
No token belongs in this profile, a URL, or a shared proxy header. Missing or
invalid adapter configuration fails without a direct fallback for these routes.

The controller must support `/api/device-transport` before the site opts in.
Only the fixed pairing, device poll/ack/result, notifications and device
runtime-diagnostics routes are accepted. Administrative command submission,
pairing approval and arbitrary upstream addresses are excluded. The response
retains the original HTTP status, content type, diagnostics epoch and body;
notification images retain their existing size and lifetime checks.

For an explicitly configured public alias, hosted pairing also supplies
`server_address`. The controller must validate the alias and bind its approval
to the selected address. Existing direct clients omit this field and retain
canonical discovery. Do not change global DNS discovery to an unsupported
proxy endpoint merely to rename the hosted address.

## Typed player preferences

Use `ott t1 settings` to discover supported preferences, `ott t1 setting bufSize` to read one, or `ott t1 setting bufSize 3` to save with type and revision checks. [Typed settings and independent VPortal configuration](remote-player-settings.md) describes stored versus effective values, scope, conflicts, standby behavior and troubleshooting.

Hosted transport bases must use canonical HTTPS URLs without a trailing slash or an explicit default port. Noncanonical configuration is rejected so discovery and transport bind exactly the same server address.
